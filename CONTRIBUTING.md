# Contributing to SFMPAS

Thanks for your interest. SFMPAS began as an MSc dissertation, so the codebase is written
to be *read* as much as run — comments explain **why** a decision was made, not what a line
does. Contributions that keep that quality are very welcome.

---

## Ways to contribute

- **Bug reports** — especially on devices or Android versions I could not test.
- **Reproduction attempts** — independent runs of `train_pad.py` are valuable. If your
  numbers differ from the published ones, that is a finding worth an issue.
- **New experiments** — other backbones, quantisation-aware training, additional PAD
  datasets (LivDet), different preprocessing ablations.
- **The known limitations** in [SECURITY.md](SECURITY.md) — particularly integrating a real
  external fingerprint scanner SDK, which is the single biggest gap.
- **Documentation** — if something in the setup did not work for you, say so.

⚠️ **Security issues do not go in the public tracker.** Follow the private disclosure
process in [SECURITY.md](SECURITY.md).

## Getting set up

```bash
git clone https://github.com/<your-username>/sfmpas.git
cd sfmpas

# ML pipeline
python -m venv tfenv && tfenv/Scripts/activate    # Linux/macOS: source tfenv/bin/activate
pip install tensorflow==2.21.0 opencv-python scikit-learn matplotlib pillow

# Backend
cd sfmpas-backend && pip install -r requirements.txt
```

The Android app opens in Android Studio (Ladybug or newer) — select the `SFMPASApp/` folder
itself, not the repository root.

**You will need SOCOFing** for anything touching the model; it is not redistributed here.
See the Dataset section of [README.md](README.md).

## Before you open a pull request

### Verify your change

There is no CI yet, so please run what applies:

```bash
# Backend — exercises all four endpoints against a running server
cd sfmpas-backend && python test_api.py --base-url http://localhost:8000

# ML pipeline — ~1 minute, confirms the whole path still executes
python train_pad.py --limit 600 --epochs 2 --tag smoke

# Android — build, then tap "Run PAD self-test" on the Home screen
```

The **PAD self-test matters most** for any change touching preprocessing. It compares the
on-device CLAHE + bicubic chain against reference fixtures generated by the Python pipeline
and reports the pixel-level divergence. If your change moves that number, say so in the PR.

### Claims about results

If you report new metrics, state the **split protocol** and the **preprocessing** — the
results table shows those two factors moving ACER by nearly 20×, so a number without them
is not interpretable. Prefer subject-disjoint splits for anything you want taken as a
generalisation claim, and report worst-case PAI APCER alongside the average, per
ISO/IEC 30107-3.

## Code style

**Python** — PEP 8, 4-space indent, ~88 column soft limit, type hints on public functions,
docstrings on anything non-obvious.

**Kotlin** — official Kotlin style, 4-space indent, ~100 column soft limit, KDoc on public
API.

**Both** — the house rule is that comments carry the *reasoning*. Compare:

```python
# Bad:  truncate to int and floor at 1
# Good: OpenCV truncates to int and floors at 1 — with small tiles this often
#       lands on 1, which is aggressive but is exactly what training used.
```

If you are working around a platform quirk, a library bug, or a non-obvious constraint,
write that down. Future readers cannot recover it from the code.

### Things to be careful with

**The preprocessing contract is load-bearing.** `PadInferenceEngine.kt` and the `enhance()`
function in `train_pad.py` must stay in lockstep — CLAHE clip 2.0 / 8×8 tiles, bicubic to
224×224, single channel replicated to three, float32 in **0–255 and not divided by 255**
(MobileNetV3's rescaling layer is baked into the graph). A change on one side without the
other silently destroys accuracy rather than failing loudly.

**The tier boundaries are duplicated by necessity.** `KycTier.kt` and `tier_for_amount()`
in `main.py` implement the same rule on device and server. If you change one, change both,
and keep the boundary convention: ₦50,000 and ₦200,000 both fall in Tier 2.

**Do not weaken the challenge protocol.** Server-issued, single-use, expiring, and bound to
one user and amount. If a change makes any of those optional, explain why in the PR.

## Pull request process

1. Branch from `main` — `feature/...`, `fix/...`, or `experiment/...`.
2. Keep commits focused; write messages that say why, not just what.
3. Update `README.md` if you change behaviour, and `SECURITY.md` if you change the threat
   model or what data is stored.
4. Open the PR describing **what changed, why, and how you verified it.**
5. Confirm you have **not** committed dataset files, `.npy` caches, `.keras` checkpoints,
   `local.properties`, or any secret. `.gitignore` covers these, but check `git status`.

Expect review comments — usually about reasoning that is clear in your head but not on the
page.

## Reporting bugs

Please include:

- What you expected and what happened instead
- Component: model / Android app / backend
- Versions — Python, TensorFlow, Android API level, device model
- For the app: the on-screen log from the Authentication screen, and the PAD self-test output
- For the backend: the request, the response, and the server log line

A failing case with concrete inputs is worth far more than a description.

---

## Code of conduct

Be straightforward and courteous. Critique the work, not the person. Assume good faith,
especially across the language and time-zone differences an open project brings. Harassment
of any kind is not acceptable and will result in exclusion from the project.
